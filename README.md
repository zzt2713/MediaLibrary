# 媒体资源库 — Modern Media Library

基于 **C++17 / Qt 6 Widgets** 的本地媒体资源管理器。把本地的图片、视频、音频统一纳入一个资源库，提供目录管理、快速检索、缩略图浏览、元数据查看、媒体预览与播放历史。

界面为深色现代化风格：左侧导航（智能分组 + 目录树 + 标签）、中间缩略图网格或列表、右侧详情面板、顶部一体化工具栏。

## 一、快速开始

### 环境要求

| 项目 | 要求 |
|---|---|
| Qt | 6.2 或更高 |
| 编译器 | MSVC 2019/2022、GCC 9+、Clang 10+ |
| C++ 标准 | C++17 |
| 构建系统 | qmake（`Album.pro`） |
| 必需模块 | `core gui widgets sql multimedia multimediawidgets` |

### 构建

```bash
qmake Album.pro
# Windows / MSVC
nmake release
# Linux / macOS
make -j$(nproc)
```

用 Qt Creator 的话直接打开 `Album.pro` 选好 Kit 构建即可。

> **本项目不引入任何第三方库。** 缩略图、查重、EXIF 解析全部基于 Qt 自带能力实现，`qmake` 之后可以直接编译，不需要额外配置 include/lib 路径。

### 部署（Windows）

```bash
windeployqt --multimedia <构建目录>\release\MediaLibrary.exe
```

`--multimedia` 必须加，否则 `QMediaPlayer` 会因为缺少解码后端而无法播放。

### 运行

程序启动后是空的。点左上角 **+** 选择目录，或直接把文件夹拖进窗口，即可开始建立索引。

## 二、功能

### 资源管理

- 递归扫描目录，按扩展名识别图片、视频、音频
- 左侧目录树与中间缩略图网格 / 列表视图切换
- 图片预览（缩放、平移、适应窗口、原始尺寸）
- 视频播放、音频播放（进度拖动、音量、静音、续播）
- SQLite 保存目录索引、收藏状态、标签、播放历史
- 文件变更后自动感知并增量刷新，处理文件删除与移动

### 工程能力

- **异步扫描与缩略图生成**：`QThreadPool` + `QRunnable`，UI 全程不阻塞
- **任务队列与并发控制**：`QSemaphore` 限制同时运行的任务数，支持取消与进度反馈
- **两级缩略图缓存**：内存 LRU + 磁盘缓存，跨启动复用
- **数据库访问封装**：按线程分配连接，批量写入走事务
- **搜索、筛选与排序**：按名称、类型、时间、大小、标签、收藏状态
- **异常处理**：损坏图片、无权限目录、失效文件、任务取消、窗口关闭时的任务清理

### 进阶功能

- 图片重复检测：MD5 精确重复 + dHash 感知哈希相似检测
- EXIF 元数据：拍摄时间、相机型号、原始分辨率
- 大型资源库管理：分页查询 + 网格懒加载
- 文件系统监控：`QFileSystemWatcher` + 去抖 + 周期性对账

### 主窗口的职责边界

`MainWindow` 只做协调，不承载业务。判断标准是"这段逻辑是否只有在这个窗口里才说得通"：

| 内容 | 放在哪里 | 原因 |
|---|---|---|
| 扫描、查重、哈希、缓存 | `core/` | 与界面无关，可在工作线程跑 |
| 搜索 / 排序 / 筛选规则 | `model/` | 属于数据视图 |
| 控件状态与联动（图标随选中态、标签随滑块） | 各自的 `ui/` 组件 | 谁持有控件谁维护它 |
| 菜单项 | `MainWindow` | 菜单不持有状态，只触发一次动作，拆出去仍要来回传同一套回调 |

### 运行时文件位置

全部由 `AppPaths` 统一决定，**不写入程序安装目录**（安装目录通常只读，且卸载时数据会一并删除）。

| 文件 | 位置（Windows 示例） |
|---|---|
| 数据库 | `%APPDATA%\MediaLibrary\MediaLibrary\library.db` |
| 日志 | `%APPDATA%\MediaLibrary\MediaLibrary\logs\app-YYYY-MM-DD.log` |
| 设置 | `%APPDATA%\MediaLibrary\MediaLibrary\settings.ini` |
| 缩略图缓存 | `%LOCALAPPDATA%\MediaLibrary\MediaLibrary\cache\thumbnails\` |

### 数据流


## 四、关键技术方案

### 1. 线程模型

这是本项目最需要讲清楚的部分，也是最容易写错的地方。

| 对象 | 所属线程 | 说明 |
|---|---|---|
| 所有 UI 对象 | 主线程 | 只有主线程可以碰 UI |
| `MediaModel` | 主线程 | 被视图直接调用 |
| `ThumbnailCache` | 主线程 + 工作线程 | 内部 `QMutex` 保护，两端都安全 |
| `MediaDatabase` | 主线程 + 工作线程 | **按线程分配独立连接**（见下） |
| `TaskQueue` 对象本身 | 主线程 | 它的信号槽在主线程执行 |
| `ScanTask` / `ThumbnailTask` 的 `runTask()` | 工作线程 | 只做纯计算与 IO |

**SQLite 的线程访问**：`QSqlDatabase` 不能跨线程共享，一个连接只能在一个线程使用。`MediaDatabase::connectionForCurrentThread()` 为每个线程创建独立连接，连接名为 `基础名 + 线程指针地址`。因此工作线程可以直接调 `upsertItems()` 写库，不需要把数据绕回主线程。关闭时统一收集所有连接名逐个 `close()` + `removeDatabase()`，避免 Qt 的 "connection is still in use" 警告。

**跨线程通信**：工作线程拿到的结果通过 `QMetaObject::invokeMethod(this, lambda, Qt::QueuedConnection)` 排回主线程。**一个关键细节**：跨线程传递的图像必须是 `QImage` 而不是 `QPixmap` —— `QPixmap` 是绑定到平台后端的绘制设备，只能在 GUI 线程使用；在工作线程创建或使用它是未定义行为。所以工作线程一律产出 `QImage`，转换到 `QPixmap` 的时机推迟到 GUI 线程真正要绘制时。

**取消的传递**：`ScanTask` 的 `runTask()` 是同步阻塞的，没法在中途调 `scanner.cancel()`。解决办法是在批次回调里做**时间心跳**——每处理一批文件检查一次是否已过去 200ms，到了就检查取消标志。用时间而不是文件计数，是因为"每 N 个文件检查一次"在文件数少的目录里永远不会触发，而扫描恰恰容易在小而多的目录上耗时。

### 2. 并发控制

`TaskQueue` 用 `QSemaphore` 而不是单纯依赖 `QThreadPool::setMaxThreadCount()`。

原因是两者的语义不同：线程池限制的是**占用的线程数**，而缩略图任务几乎所有时间都在等磁盘 IO 和图像解码。如果并发数完全放开，会同时解码几百张图把内存打爆。

所以这里把"并发任务数"和"线程数"解耦：`QSemaphore` 限制同时在跑的任务数（默认 `idealThreadCount()`，夹在 `[4, 8]`），线程池则留出余量（上限 `max(8, 并发数 × 2)`）。每个任务 `run()` 时 `acquire`、结束时 `release`，超出上限的任务阻塞在 `acquire` 上排队——内核级阻塞，不占 CPU，也不需要轮询。

默认值取核数而不是固定 4，是因为解码是纯 CPU 且单张图不并行：8 核机器上用 4 个并发会空着一半核心，大目录里表现为缩略图一张张慢慢冒出来。上限 8 是考虑机械盘和网络盘——并发再高会因寻道竞争反而变慢。用户可在「设置 → 高级 → 后台任务并发数」手动指定 1-32 覆盖它。

窗口关闭时 `cancelAllAndWait()` 会设置取消标志、清空排队任务、等待工作线程退出。**这一步是必须的**：否则工作线程可能还在访问 `MediaDatabase`，而它随后被析构，导致 use-after-free。

### 3. 两级缩略图缓存

```
查询 ──► 内存 LRU ──命中──► 返回
           │未命中
           ▼
        磁盘缓存 ──命中──► 回填内存 ──► 返回
           │未命中
           ▼
        解码生成 ──► 写入两级缓存 ──► 返回
```

**缓存键**：`路径 + mtime + size + 边长` 的 MD5 摘要。

把 `mtime` 和 `size` 放进键里是刻意的设计：文件一改动，键就变了，旧缓存自然再也命中不了，等价于已失效。这比"监听文件变化再主动删缓存"更可靠 —— 不会漏删，不需要跨进程协调，也不需要维护"路径 → 缓存文件"的映射表。代价是磁盘上会残留一些永远命中不了的冷数据，由 `enforceDiskLimit()` 按最后访问时间回收。

**内存层按字节数而非条数限制**（默认 128MB）。同样 1000 条缓存，缩略图尺寸不同可能相差十倍，按条数控制会导致大缩略图时内存爆掉。

**淘汰策略**：超限时按访问序号排序，淘汰到容量的 80%（而不是刚好卡在上限），避免在边界反复触发排序。正常路径下零开销。单张超过内存上限 1/4 的缩略图会跳过内存层直接落盘，防止一张图挤空整个缓存。

**磁盘写入原子性**：先写 `.tmp` 再 `rename`，避免程序中途退出留下半截 PNG 被当成有效缓存。

### 4. 缩略图生成的性能要点

最关键的一点是**在解码阶段就缩小**：

```cpp
QImageReader reader(path);
const QSize target = original.scaled(edge, edge, Qt::KeepAspectRatio);
reader.setScaledSize(target);   // 解码器直接按目标尺寸解
const QImage image = reader.read();
```

而不是先 `reader.read()` 解出完整图片再 `scaled()`。对一张 6000×4000 的照片，前者的解码输出约为 1MB，后者要先解出约 96MB 的完整位图再缩。实测差距在一个数量级左右，内存峰值尤其明显。

`setScaledSize` 在个别格式上会被忽略，所以代码里保留了一道 `scaled()` 兜底。

**绘制侧同样要缓存，否则解码白优化。** 模型里存的是 `QImage`（跨线程安全），绘制只能用 `QPixmap`，转换必须在 GUI 线程做。`ThumbnailDelegate` 因此缓存两样东西：

| 缓存 | 内容 | 不缓存会怎样 |
|---|---|---|
| `m_pixmapCache` | **已缩放到缩略图区域**的 `QPixmap`（键是 itemId，附存来源图的 `cacheKey()` 用于识别换图） | 每帧对每张可见缩略图重做 `fromImage` + 平滑缩放，几十项 × 每次重绘，滚动直接卡顿 |
| `m_placeholderCache` | 加载中占位图，键是「类型 + 时长文本 + 目标尺寸」 | 占位图也要走 `makePlaceholder` + `fromImage` + 缩放，而加载期整个屏幕都是占位图——这段正是用户觉得"转半天"的时间 |

`m_pixmapCache` 按总字节数设了 64MB 上限。这个上限是必要的：缩略图尺寸最大 320×320，单张约 400KB，而缓存键是 itemId——如果不限制，用户滚动浏览一遍大目录就会按"看过的条目数"一路涨上去。超限时整体清空，重算只涉及当前可视的几十项。

容量检查放在 `insert` **之前**，这一点是有意为之：`pixmapFor()` 返回的是指向 `QHash` 内元素的指针，调用方 `paint()` 立刻使用。如果插入之后再清理，刚插进去的那张可能被一起清掉，返回的指针当场失效。

识别"同一 itemId 换了图"用的是 `QImage::cacheKey()` 而不是 `QImage::operator==`。后者只有在两个 `QImage` 共享同一份数据时才是 O(1)，数据不同时会退化成逐像素 `memcmp`——而"数据不同"正是这里要识别的场景。

`m_placeholderCache` 的键里带了时长文本（视频占位图要画时长角标），组合数会比图像多，所以设了 24 项上限，超出整体清掉重建。

两个缓存都在缩略图尺寸变化时一并清空（`clearPixmapCache()`）。

### 5. 视图懒加载

`ThumbnailGrid` 只请求「当前可视区 + 上下各一屏」范围内的缩略图，并且滚动时按 150ms 去抖——停下来才批量请求。快速拖动滚动条时如果每帧都发请求，一瞬间会产生几百个任务，把队列塞满、把内存推高。

单批请求上限 60 个，已请求过的 id 记在 `QSet` 里避免重复。

**关键一点：一批加载完会继续下一批。** 单批上限本来是"防止一次塞爆队列"，但如果没有后续触发，打开一个大目录时首批 60 张做完就停住了，剩下的必须等用户滚动才继续——观感就是缩略图一张张慢慢冒出来。所以视图订阅了 `MediaModel::dataChanged`：每完成一张缩略图模型都会发这个信号，定时器未激活时就用它启动下一轮，形成持续填充直到可视区（含预取范围）全部就绪。

`MediaModel` 不再自己逐行发缩略图请求，只维护每个条目的加载状态，具体请求由视图按可视区发起——模型不知道"哪一屏看得见"，让它决定请求范围并不合适。

> `MediaModel::thumbnailRequested` 信号目前工程内**没有任何接收者**（接收端连的是 `ThumbnailGrid::requestThumbnail`）。它一直是空转的，所以删掉那些 `emit` 是死代码清理，对加载速度没有贡献——速度上的改动是上面那条"批次衔接"和绘制缓存。信号声明本身作为公开 API 保留。

### 6. 增量同步

`MediaDatabase::upsertItems()` 是增量同步的核心。对每个扫描结果按 `path` 查已有记录：

| 情况 | 处理 |
|---|---|
| 记录不存在 | INSERT |
| 存在但 `mtime` 或 `size` 变了 | UPDATE，并**清空 `content_hash` / `visual_hash` / 尺寸**，让后台重新计算 |
| 存在且未变 | 跳过，只复位 `missing` 标记 |

第三点很重要：**未变化的记录不会被覆盖**，所以用户设置的收藏与标签在重新扫描后依然存在。

失效处理用的是"标记"而不是"删除"：扫描完一个目录后，把本次没见到的记录标 `missing = 1`。用户可能只是临时把移动硬盘拔了，物理删除会连带丢掉收藏信息。真正清理失效记录是用户在菜单里显式触发的操作。

### 7. 重复检测

算法在 `media/core/DuplicateService`，界面只负责进度对话框与结果提示。

- **精确重复**：分块计算文件 MD5（1MB 一块）。大视频动辄几个 GB，一次性 `readAll()` 会直接把内存打爆。
- **视觉相似**：dHash（差分感知哈希）。缩放到 9×8 灰度，逐行比较相邻像素亮度，得到 64 位摘要。汉明距离 ≤ 8 判为相似，对缩放、轻微压缩、亮度调整不敏感。
- 哈希是增量计算的：`itemsWithoutHash()` 只取还没算过的记录，所以第二次执行几乎是瞬时的。
- 两种检测都通过 `const Result &` 一次返回分组结果，界面把它铺平成虚拟列表喂给模型后切到「重复项」分组；同组条目相邻排列，便于比对。

`DuplicateService` 暴露的是两个方法（`findExactDuplicates` / `findSimilarImages`）而非一个带 bool 开关的方法：两条路径的规模上限、阈值语义和增量策略都不同，合成一个入口只会让内部再分叉一次。

## 六、日志

日志是排查问题的主要手段，尤其在本项目这种"多线程 + 异步任务"的场景里。

- 位置：`AppPaths::logFile()`，按日期分文件（`app-2026-05-14.log`）
- 格式：`时间 | 级别 | 线程 | 分类 | 函数 | 消息`
- 级别：`DEBUG` / `INFO` / `WARNING` / `ERROR`，可在 **设置 → 高级** 里即时调整

线程标识（`T0001` 这类短标签）是刻意保留的：跨线程任务出问题时，
"这行日志是哪个线程打的"经常比"哪个文件"更关键。

```
2026-05-14 09:03:12.451 | INFO  | T0a3c | Task     | ScanTask::runTask | scan finished: D:/Photos affected=1247 discovered=1247
```

日志在每条写完立即 flush。代价是少量性能损失，换来的是**程序崩溃时最后几条日志不会丢** ——
而那几条恰恰是定位崩溃原因的关键。

## 七、已知限制

这些是真实存在的限制，不是"待办清单"式的客套。

### 功能限制

1. **视频与音频没有真实缩略图。** 视频抽帧需要额外解码库（如 FFmpeg），音频封面需要解析 ID3 标签。为了保持"零第三方依赖"，这两类资源使用带类型标识与时长角标的占位图。这是本项目最明显的功能缺口。

2. **EXIF 解析依赖 `QImageReader` 的文本元数据表。** 字段覆盖率取决于 Qt 的图像插件，某些相机写入的非标准标签读不到。没有引入 `libexif` 是同样的取舍。

3. **感知哈希查重是同步执行的。** 几万张图片时会明显卡住界面（因此代码里加了 `QProgressDialog` 和一个 2000 张的处理上限）。正确做法是把它也做成后台任务，但那需要处理"后台算完如何通知 UI 更新分组"的完整链路，本版本先用同步实现保证功能可用。

4. **搜索只覆盖已加载的数据。** 输入时的即时筛选发生在代理模型层，范围是当前已加载的页；走数据库的全库查询需要额外触发。两者同时生效会产生"结果不稳定"的观感，所以做了取舍。SQL 的 `LIKE '%x%'` 无法利用索引，在大库上比内存筛选更慢。

5. **音频没有波形显示**，只有一个音符占位。

6. **重命名功能未实现**（按 `F2` 会明确提示，而不是静默无反应）。

7. **"取消全部"不能停止正在进行的扫描。** 任务面板的"取消全部"目前只停止缩略图生成；要停扫描需要 TaskQueue 暴露一个队列级取消的公开接口，而当前该能力只用于程序退出时的收尾。这是已知的功能缺口，不是隐藏行为。

### 已知缺陷（已修复，保留记录）

1. **视图的 `selectionChanged` 曾经从未连上，"选择"只有鼠标单击这一条路生效。**

   原来的代码在 `ThumbnailGrid::setupGrid()` / `setupList()` 里连视图的
   `selectionModel()->selectionChanged`。但连接时视图刚构造完，
   `QAbstractItemViewPrivate` 的构造函数把 `selectionModel` 初始化为 `nullptr`
   （`qabstractitemview.cpp:44` 起），`selectionModel()` 返回空指针，
   那个 `if (selectionModel())` 判断永远不成立 —— 连接从未建立。
   而真正的选择模型是稍后 `QAbstractItemView::setModel()` 内部新建并
   `setSelectionModel()` 换上去的（同一文件），所以必须在 `setModel()` 之后连。

   修复前的表现：`clicked → onItemClicked` 这条独立路径仍在工作，所以鼠标单击
   详情面板会跟着变；但键盘方向键、框选、Ctrl+A 全选，以及多选后的
   "已选 N 项"汇总（`MainWindow::onSelectionChanged` 里 `selected.size() > 1` 分支）
   都不再通知外部。

   现已把这两个 `connect` 移到 `ThumbnailGrid::setModel()` 里
   （`m_grid->setModel(proxy)` / `m_list->setModel(proxy)` 之后），
   槽是成员函数指针，因此可以加 `Qt::UniqueConnection`
   保证 `setModel()` 重复调用时不会叠加连接。

   `onItemClicked` 里的那次 `emit selectionChanged` 保留了：单击一个已经选中、
   且是唯一选中项的条目时，选择集合没有变化，`QItemSelectionModel` 只发
   `currentChanged` 而不发 `selectionChanged`，此时只有那条路径能通知外部。
   代价是普通单击会发两次通知，但上层是幂等的
   （`DetailPane::showItem` 直接覆盖，`TaskManager::requestThumbnail` 按
   `m_thumbEdgeByItem` 去重），只是多一次重绘。

### 设计取舍

1. **不提供删除物理文件的功能。** `Delete` 键只从索引里移除记录。这是刻意的：媒体库工具的误删代价太高，删除文件交给文件管理器。

2. **目录树的预建深度上限为 4 层**，且只包含"子树里有资源"的目录。更深的层级在展开时不会继续预建，避免一棵巨树拖慢建树本身。

3. **文件监控上限为每个根目录 64 个子目录、全局 256 个。** `QFileSystemWatcher` 在 Windows 上底层用 `ReadDirectoryChangesW`，每个被监控目录占一个句柄；Linux 上受 inotify watch 数限制。超出部分靠 30 秒一次的周期性对账与手动刷新兜底。

4. **文件系统监控做了去抖（800ms）与节流（同目录 3 秒内不重复扫描）。** 复制一个含 500 张图的文件夹会瞬间产生几百次目录变更事件，每次都触发重扫等于把磁盘打满。

5. **扫描期间挂起文件监控。** 扫描会更新文件的访问时间，某些系统上会触发变更事件，不挂起可能造成"扫描 → 事件 → 再扫描"的循环。

## 八、性能数据

以下是在 Windows 11 / MSVC 2022 / Qt 6.8 上，对约 12000 个媒体文件（图片为主，含约 800 个视频）的实测观察。

| 指标 | 数值 | 说明 |
|---|---|---|
| 首屏显示耗时 | < 200ms | 分页加载首批 200 条，不等待全量扫描 |
| 首次全量扫描 | 约 45s | 含 EXIF 读取；关闭 EXIF 后约 22s |
| 二次启动 | < 1.5s | 直接查库，不重新扫描 |
| 缩略图生成 | 约 12ms / 张 | 4000×3000 JPEG，解码阶段缩放 |
| 滚动帧率 | 稳定 60fps | 懒加载 + 去抖，滚动时不发请求 |
| 内存缓存命中率 | 约 92% | 正常来回浏览场景 |
| 冷启动后二次浏览 | 约 100% 磁盘命中 | 跨启动复用磁盘缓存 |
| 常驻内存 | 约 180MB | 含 128MB 缩略图内存缓存 |

> 这些数字来自开发机上 `qDebug` 输出的计时与状态栏缓存统计，不是严格的基准测试。**建议你自己在目标机器上复现**：状态栏的缓存命中率是实时更新的，"帮助 → 性能与统计信息"里有完整的计数（内存命中 / 磁盘命中 / 未命中）。

### 优化前后的对比

| 优化项 | 优化前 | 优化后 |
|---|---|---|
| 缩略图解码 | 完整解码再缩放，约 120ms / 张，峰值内存 96MB | 解码阶段缩放，约 12ms / 张，峰值内存约 1MB |
| 数据库写入 | 逐条 commit，1 万条约 60s | 事务批量，1 万条约 2s |
| 滚动时请求 | 每帧请求，瞬间几百个任务 | 去抖 150ms + 单批上限 60 |
| 缓存键 | 只用路径，文件改了还会命中旧图 | 含 mtime + size，自动失效 |
| 内存缓存 | 按条数限制，大缩略图时内存失控 | 按字节限制 + LRU |

## 九、测试建议

### 功能验证

1. **空库启动** → 应显示引导页，不报错
2. **添加目录** → 状态栏出现扫描进度，网格逐步填充
3. **关闭后重开** → 不重新扫描，内容立即可见，收藏与标签保留
4. **修改一个文件后刷新** → 该文件的缩略图更新（缓存键里的 mtime 变了）
5. **删除一个文件后刷新** → 该条目进入"失效记录"分组，而不是消失
6. **扫描中途关窗口** → 正常退出，无崩溃、无 Qt 警告

### 异常场景

| 场景 | 构造方式 | 预期 |
|---|---|---|
| 损坏图片 | 把 `.jpg` 改成随机字节 | 显示占位图，不崩溃，不阻塞其他图片 |
| 无权限目录 | 用 `icacls` 移除读权限 | 跳过并记录警告，扫描继续 |
| 文件被占用 | 用播放器打开视频后扫描 | 跳过，不阻塞 |
| 大量文件 | 复制 1 万个文件 | 界面保持可操作，进度条推进 |
| 盘符失效 | 用 U 盘添加目录后拔出 | 标记失效，不崩溃 |
| 扫描中取消（关窗） | 大目录扫描时关窗口 | 8 秒内退出 |

### 缓存验证

1. 清空缓存 → 首次浏览某目录，观察状态栏"命中率"从低值上升
2. 重新打开同一目录 → 命中率应接近 100%（内存命中）
3. 重启程序后再浏览 → 应是磁盘命中
4. 修改某张图的内容（保持文件名）→ 该图缩略图应更新

## 十、可扩展方向

按投入产出比排序：

1. **给 TaskQueue 加队列级取消的公开接口** —— 目前"取消全部"停不了正在进行的扫描（见已知限制 7），缺口最小、收益最直接
2. **把感知哈希查重移到后台线程** —— 目前的同步实现是最明显的体验短板
3. **接入 FFmpeg 生成视频缩略图** —— 需要引入依赖，但能补齐最明显的功能缺口
4. **后台为缩略图任务排优先级** —— 目前可视区与非可视区任务同权，快速滚动时可能被远处的任务抢占
5. **拼音首字母搜索** —— 中文场景下比子串匹配好用得多
6. **虚拟滚动** —— 目前已用 `setUniformItemSizes` + 分页 + 懒加载，可进一步换成自绘虚拟列表以支撑十万级条目
7. **多选批量操作**（批量加标签、批量收藏）
8. **导入 / 导出收藏与标签**（JSON），便于迁移
9. **可切换的浅色主题** —— `ThemeManager` 已把所有颜色集中管理，QSS 用占位符注入，加一套色板即可支持
